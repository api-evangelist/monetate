# Request decisions from the Monetate engine

The Engine API has exactly **one** operation. Everything Monetate can decide — which experience
variant to serve, which recommendations, which social-proof message, which badge, which redirect — comes
back from a single `POST /decide/{retailerShortname}`, and the shape of the request is what varies.

## Before you start

- `retailerShortname` is your account's shortname. It is in the base URL shown on your own API
  documentation inside the Monetate platform.
- **This endpoint takes no credentials.** The published Swagger 2.0 document declares no
  `securityDefinitions` and no `security` requirement — identity comes from `retailerShortname` in the
  path plus `channel` in the body. Do not attach the Auth API token here; it belongs to the Data and
  Metadata APIs only (see `authentication/monetate-authentication.yml`).
- Pick a host. `engine.monetate.net` is the default. Regional hosts are `engine-global.monetate.net`,
  `engine-us-east-1.monetate.net`, `engine-us-west-2.monetate.net` and `engine-eu-west-1.monetate.net`;
  the SDKs select one with the `engineHostName` field on the Account object.

## Step 1 — Identify the shopper

The request body (`HttpRequestBody`) carries three identity fields and you must send at least one:

| Field | Meaning |
|---|---|
| `monetateId` | Monetate's own persistent device id. Generated by Monetate when you send neither this nor `deviceId`, or read from the `mt.v` cookie on a JavaScript-integrated domain. |
| `deviceId` | Your own persistent device identifier (e.g. iOS `identifierForVendor`), accepted in place of `monetateId`. |
| `customerId` | Identifies the person across devices. |

Also send `channel` (the string identifying account, domain and instance) and, if you are inside an
SDK, `sdkVersion`.

**On a first request** send no `monetateId`. Monetate mints one and returns it in `meta.monetateId`.
Persist it and send it on every subsequent request for that device, or you will fragment the session and
the engine will decide against an empty history.

## Step 2 — Build the events array

`events` is required and is an array of `Event` objects, each discriminated by an `eventType` string.
Three families exist and a single request usually mixes all three:

- **`monetate:context:*`** — what is true right now. `PageView`, `Cart`, `AddToCart`, `Purchase`,
  `ProductDetailView`, `ProductThumbnailView`, `ProductThumbnailSkuView`, `ContentView`, `SearchView`,
  `Referrer`, `IpAddress`, `UserAgent`, `Language`, `ScreenSize`, `Coordinates`, `CustomVariables`,
  `Metadata`.
- **`monetate:decision:*`** — what you are asking for. `DecisionRequest`, `ServerSideRequest`,
  `PersonalizationFlagRequest`.
- **`monetate:record:*`** — what already happened, reported back for measurement. `PageEvents`,
  `Impressions`, `RecImpressions`, `RecClicks`.

Send context before you ask. The engine decides on the state you have just given it in the same call.

## Step 3 — Read the response

`HttpResponseBody` is `{ "meta": {...}, "data": {...} }`:

- `meta.code` — the HTTP status, repeated in the body.
- `meta.errors[]` / `meta.warnings[]` — untyped objects. The spec does not describe an individual
  error's shape, so treat these as opaque and log them rather than branching on them.
- `meta.monetateId` — capture it on the first call and reuse it.
- `data.responses[]` — one entry per decision request, each with a `requestId` and an `actions[]` array.

Each action carries an `actionType` naming its `monetate:action:*` model — `OmnichannelJson`,
`OmnichannelHtml`, `DynamicHtml`, `OmnichannelRecommendation`, `OmniChannelImageBadging`,
`OmnichannelRedirect`, `SocialProofDataV2`, `CmsAction`, `ContentstackCMSAction`, `ApiAction`,
`GlobalApiAction`, `VariantSelector`, `DataCollection`, `OpenAction`, `NoAction`,
`ResponsysTriggeredEmail`, `ResponsysTriggeredCustomEvent`. Branch on `actionType`; each has its own
model page under `https://developer.monetate.com/engine-api/`.

`NoAction` is a normal, expected result. It means the shopper did not qualify for anything — it is not
an error.

## Step 4 — Report impressions

An action you rendered is only measured if you say so. Each action carries an `ImpressionReporting`
block; send the corresponding `monetate:record:Impressions` (or `RecImpressions` / `RecClicks` for
recommendations) on a later call. If you skip this, the experience will appear to have zero traffic in
analytics even though it served.

`monetate:record:EndcapImpressions` and `monetate:record:EndcapClicks` are **deprecated** — use
`RecImpressions` and `RecClicks`.

## Error handling

The spec declares only two responses:

- `200` — succeeded; `data.responses[].actions` may still be empty or `NoAction`.
- `400` — "the request was either malformated (did not follow this specification), or the data sent was
  invalid." Validate your event batch before sending; the error body will not tell you which field.

Nothing else is documented. There is no published behaviour for auth failures, throttling or engine
outages on this endpoint, and no `Retry-After`. **The endpoint is not idempotent and offers no
idempotency key** — a retried request with `monetate:record:*` events will double-count impressions.
Retry decision-only requests freely; never blind-retry a batch containing record events.

## Preview an unpublished experience

Set `preview` in the body to the token generated by the PREVIEW button on the Experience Editor page.
That returns actions for a specific variant even when the experience is not live. Never ship a preview
token to production traffic.
